# 22/26 漏检的失败分类（2026-10-21）

**结论：低检出率主要卡在候选发现，不在取证/准入门控。** 26 个有效参考缺陷对里，候选命中 4 个、有效证据 1 个；22 个漏检中：

- **8 个完全没有候选**（模型返回 0 条 LLM finding，36% 的漏检）；
- **14 个有候选但偏题**（64% 的漏检），其中 4 个还复现了额外问题，但没有打中参考根因；
- 另有 **3 个候选命中但证据失败**，1 个有效证据（PySnooper-3）。

这解释了为什么继续优化 Docker、契约审计或准入的收益上限很低：**22/26 的问题在候选阶段就已经丢了。**

| 类别 | 数量 | 案例 |
|---|---:|---|
| 有效证据 | 1 | PySnooper-3 |
| 候选命中但证据失败 | 3 | tornado-4、youtube-dl-11、youtube-dl-6 |

合计 26 个有效对；候选命中率 4/26（15.4%），有效证据率 1/26（3.8%）。

## 8 个“完全没有候选”说明了什么

这 8 个 buggy 侧报告里没有任何 LLM finding，运行状态大多是 `completed`，调用只有 1–2 次：

| 样本 | 调用 | 参考问题类型 |
|---|---:|---|
| tornado-3 | 2 | weak cache 已清理后的 close 异常 |
| tornado-5 | 1 | 时钟回拨时 `_next_timeout` 不推进 |
| tornado-7 | 2 | `concurrent.futures.Future` 不可原生 await |
| tornado-8 | 1 | WebSocket 头 ValueError 在捕获块之外 |
| tornado-9 | 1 | `url_concat(url, None)` 应返回 url |
| youtube-dl-1 | 1 | 布尔 False 被当成“存在” |
| youtube-dl-2 | 2 | DASH format_id 非唯一导致格式丢失 |
| youtube-dl-3 | 1 | HTML 实体 regex 吞并相邻实体 |

这不是“测试写不出来”，而是模型**没有提出任何候选就结束了**。当前提示允许“可以为空”，但没有任何机制要求模型先枚举输入变体、状态/生命周期、协议分支或跨文件契约；模型很容易看一眼就返回 `{"findings":[]}`。

## 14 个“有候选但偏题”说明了什么

这些案例中模型确实在读代码、也提出了 1–4 条候选，但讨论的是邻近分支、错误输入、错误异常类型或额外问题，不是参考根因。典型模式：

- **输入变体没有覆盖**：`None`、`False`、`0`、空列表、bytes/str、非法 URI、零参数调用、时钟回拨等。
- **状态/生命周期没有追**：weak cache、IOLoop registry、Future/await、连接关闭、UI helpers 生命周期。
- **协议/头部细节没有核**：chunked 大小写、Transfer-Encoding、WebSocket headers、Range 边界。
- **regex/编码没有逐字符推**：转义 `n/u`、escaped apostrophe、HTML 实体、科学计数法。
- **跨文件/数据来源没有追**：DASH format_id、fallback selector、网页 JSON 章节元数据。

这些都不是“上下文不够多”能直接解决的；r0 的 callgraph 扩充没有带来参考命中。更像是**缺少一套“先理解契约、再枚举反例”的推理流程**。

## 3 个“候选命中但证据失败”

- **tornado-4**：候选正确指出 `bytes=-100` 导致负 start，但生成测试复制了处理逻辑，没有调用目标方法，判 `unrelated_failure`。
- **youtube-dl-11**：候选找到整数输入触发 `re.sub` TypeError，但声称预期返回 `None`，与参考修复“返回输入本身”不同，`unsupported`。
- **youtube-dl-6**：候选识别缺 `dur`/`begin` 的 KeyError，但生成格式/契约失败，未形成有效证据。

这说明取证阶段也有真实问题，但它只影响 4 个已识别候选中的 3 个；**在 22 个漏检上，取证阶段根本没有机会发挥作用。**

## 对“审查流程是否有问题”的回答

**是，但问题在发现阶段的工作方式，不是 Docker/报告/准入门控。**

当前发现阶段更像“单次广撒网”：

- 一次调用，给代码 + 上下文；
- 要求“优先发现能构造最小输入验证的行为缺陷”，最多 4 项、可以为空；
- 没有强制的契约理解、输入变体枚举、假设—反例步骤；
- 工具最多 2 轮，但很多窗口只用 1 次调用、不读调用方/文档/测试；
- 候选必须在当前 chunk 行号内，跨文件综合能力弱。

这会导致两类失败：不确定时返回 0 条（8 个），或者报邻近问题（14 个）。所以下一步应该改**发现流程**，不是继续加取证门控。

## 对 P1 的直接启示

1. **对 8 个无候选**：要求模型先做检查清单，再允许返回 0；零候选必须附带“检查过哪些输入/分支/外部定义”。这可以直接针对“看一眼就结束”。
2. **对 14 个偏题**：要求每个保留假设写清“契约/前置条件 + 最小反例 + 预期 vs 可能实际”，并至少核对一个调用方/被调用定义/文档/测试；只报有具体反例的候选。
3. **对 3 个证据失败**：等候选召回上来后再改测试生成/契约；现在做收益有限。
4. **不建议**：继续加 callgraph 上下文、开 thinking、提高输出上限、收紧准入；这些已经被实验证明不是主要杠杆。

## 方法与限制

- 分类只使用 2026-10-14 冻结的 72 次报告、判读和运行记录，0 次模型调用、0 次 Docker。
- “完全没有候选”指 buggy 侧报告没有任何 LLM finding；静态 Ruff/Bandit 建议不算候选。
- “偏题”不自动等于误报；额外复现的问题可能真实，只是不匹配参考问题。
- 26 个有效对是已知位置窗口，不是全仓库召回；判读为模型辅助、人工复查待完成。
- 分类脚本：[evidence_failure_taxonomy.py](../../evaluation/evidence_failure_taxonomy.py)；结构化结果：[taxonomy.json](taxonomy.json)。

## 下一步

按长期目标，下一步是 **P1：假设—反例式发现流程的单变量 A/B**。先写协议（样本、两臂、预算、指标、采用条件），再启动模型调用；不要直接改代码后跑全量。

P1 的建议指标：

- 候选识别率（参考问题）；
- 有效证据转化率；
- 额外候选数量及真实性；
- 固定侧同参考问题告警；
- 调用/tokens 与完整度。

只有在候选识别率有可复现提升、且没有增加固定侧告警和不可接受成本时，才保留流程改动。
