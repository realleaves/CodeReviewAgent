## 改了哪里

新增`src/review_context.py`，从已有CodeIndex中的源码静态建立保守的名称、作用域、导入与调用关系。evidence发现阶段可以用`--context-strategy callgraph`选择新策略：

- 优先保留包住主片段的函数签名/文档，再检索调用方附近的保护条件及实际可解析的被调用定义。
- 处理明确的导入别名、相对导入、模块限定名、嵌套函数和当前类方法。参数遮蔽、重复定义、显式属性重绑、星号导入等有歧义时不给出同名定义猜测。
- 补充相关导入片段；在已有索引文档内按函数名和词项选择片段，匹配只表明相关性，不自动认定为行为契约。
- 所有代码附实际路径及起止行，补充内容连同JSON元数据最多10000字符。主片段保持完整，不重复追加已覆盖行。
- 审查trace记录策略、输入哈希、补充字符数与引用位置，方便复查模型实际初始输入。

CLI、ReviewOptions、正式pipeline及BugsInPy运行入口已接通。模型配置、系统审查提示词、只读工具、工具轮数、候选上限、测试生成/执行/核验及已有评分逻辑均未改动。旧策略可直接作对照。

- 18组legacy输入与冻结旧代码真实构造的输入完全一致，审查系统提示词也一致。
- 18组主代码、定位范围不变；新补充的源代码行与快照逐字核对，预算全部满足，最大8838字符。
- 12/18个窗口补到了可静态建立联系的调用方片段。这是检索覆盖，不是12个模型发现或真实缺陷。
- 86项项目测试通过，其中新增21项，覆盖同名不同模块、别名、局部遮蔽、实例/模块方法重绑、循环导入、嵌套函数优先级、文档80行后匹配、预算、源码不执行、CLI管线及trace等。

## 为什么仍需模型对照

六个样本的主片段本来就包含部分关键缺陷实现；有些历史审查还通过工具读到了下游源码。此次仅核查初始输入，无法根据它断言漏检完全由信息不足导致。逐项诊断见[diagnosis.json](diagnosis.json)。

这是静态关系子集：动态实例类型、继承分派、回调注册、装饰器变换、getattr/setattr、lambda及推导式内部的调用均不保证解析；未知目标保留未知，不把静态边当作运行事实。首轮离线检查发现嵌套小函数会挤掉外层入口，已调整优先级并加回归。两个中间输入版本及对应源码仍在本地outputs中保留；没有调用模型或按模型成绩筛选实现。

采用条件仍按原实验方法：冻结实现和样本、以同模型/提示词/调用上限重复成对运行，审核正确候选、错误告警与实际成本；有稳定收益才考虑改默认值。当前没有新的检出率、精确率、有效证据转化或新样本成绩，历史1/26不变。

## 使用与复核

在原审查命令后添加参数即可选择实验策略：

```bash
.venv/bin/python main.py review examples/evidence --local --mode evidence --context-strategy callgraph
```

此命令会正常调用配置的模型并执行证据流程。只做离线上下文检查时：

```bash
.venv/bin/python evaluation/context_preview.py --output outputs/context-preview-new
python demo/context-callgraph-20261015/verify.py
```

离线preview依赖本工作区已准备的历史快照、报告和冻结基线，输出目录必须为新路径。归档校验无需这些历史目录，无模型/API/Docker调用。
