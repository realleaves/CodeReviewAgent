章节结束时间使用原始索引而非过滤后的上一章节

youtube_dl/extractor/youtube.py:1672
问题说明
循环用 enumerate(chapter_lines, start=1) 的 next_num 判断是否为最后一行，但循环体内存在 continue（start_time 为 None、end_time 为 None）和 break。当某个中间章节因 parse_duration 返回 None 被 continue 跳过时，后续章节的 end_time 仍取 chapter_lines[next_num][1]，即原始列表的下一行，而不是实际被加入的下一章节。这本身与“下一行”语义一致，但若被跳过的行恰是最后一行，则 next_num == len(chapter_lines) 成立，end_time 取 duration，而实际最后加入的章节的 end_time 应为被跳过行的解析结果（None 则跳过该章节）。更明确的问题：当某章节 start_time > duration 触发 break 时，前面已加入的最后一个章节的 end_time 已被设为该越界章节的 start_time（因为 next_num 指向它），随后被 clamp 到 duration，行为可接受。真正缺陷在于 continue 分支：若 chapter_lines[next_num][1] 解析失败，当前章节被 continue 跳过，但其 start_time 已用于前一章节的 end_time，导致前一章节 end_time 指向一个未加入章节的时间点，章节区间出现空洞或重叠。
触发条件
description 含三行章节，第二行时间点无法被 parse_duration 解析（如 '1:2:3:4' 或空），第一行 start_time 有效。
代码依据
1667-1675：start_time 解析失败 continue；end_time = parse_duration(chapter_lines[next_num][1])，next_num 为原始索引；若该值为 None 则当前章节 continue，但前一章节已用该值作为 end_time。
修复建议
先过滤出可解析的章节列表，再基于过滤后的相邻元素计算 end_time，或解析失败时回退到 duration/下一有效时间点。
复核理由
尚未复核；未运行待审代码。
验证方式
候选缺陷描述的是章节区间在解析失败时可能出现空洞/重叠，但代码中没有任何文档、测试或语言规则约定 _extract_chapters 在中间章节时间点无法解析时必须如何计算相邻章节的 end_time。现有实现（跳过无法解析的章节、用原始下一行时间点作为 end_time）本身不能证明期望行为；候选建议的“先过滤再计算”只是改进建议，不是可定位的契约。因此无法构造有来源断言的复现测试。
